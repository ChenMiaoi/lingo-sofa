# 共享本地后台服务

网页和 Discord 默认连接一个本地 Node 24 服务。首次安装助手后，任一端启用都自动启动或连接它；至少一个客户端在线则持续运行。现有明确选择的浏览器直连模式保留，该模式的凭证、预算与统计仍独立，不自动转移密钥或合并内容。

## 启动与退出

1. 本地组件读取受当前用户保护的 `runtime-install.json`，只启动其中固定的可执行文件与入口，不接受网页/renderer 传入的命令、路径或 shell 文本。
2. 发现时验证本机地址、端口范围、随机 token、协议版本及实例 ID；不信任单纯存在的描述文件。发现失败才启动服务，启动过程有等待上限。
3. 多端同时启动时，服务先独占配置端口再初始化用量。只有取得端口的进程发布 `runtime-connection.json`，竞争者退出，不写入历史。其他进程占用端口会导致明确的启动失败，不杀死未知进程。
4. 每个 native 客户端持有随机在线租约，每 15 秒续期，45 秒未续期失效。来源加租约 ID 构成隔离边界，一端不能释放另一来源的租约。
5. 最后一个租约释放或失效后等待 60 秒。期间重新连接取消退出条件；排队、执行或 Provider 保存任务未完成时不退出。
6. 退出等待 HTTP 请求完成和用量写入结束，然后删除本实例的连接文件。新服务使用新凭据。崩溃遗留描述文件会被健康探测判定为无效，下一端启动可恢复服务。

正常关闭浏览器通常关闭 native port；浏览器强制终止 native host 时使用租约过期恢复。Mac 关窗口与最小化不等于应用退出；插件停用也会释放连接。服务不设置登录自启，也不在两个客户端离线后无限驻留。

## 两端接口与信任边界

浏览器后台使用 `connectNative` 的长连接，stdio 外层 `{transportId,payload}` 只负责匹配并发响应；payload 与原有业务协议一致。Native Host 检查扩展白名单，转发到服务的 loopback API，页面不能直接访问本地程序或读取 token。Vencord native 层复用相同的服务发现/租约实现，renderer 只取得本实例连接凭据。

服务继续验证 Origin、Host、Bearer 凭据、请求 schema、大小及速率。服务状态和租约接口也需要认证；描述文件、Provider 与用量文件只对当前用户开放。凭据绑定服务实例生命周期，重启轮换；不再使用一小时后需人工重新配对的流程。安装与来源授权仍是明确的首次操作，不自动安装系统组件。

控制通道可以重连；已发送翻译/问答绝不自动重放。断开时未返回 usage 的请求仍记录未知，严格预算继续暂停；重启不是清空预算的方法。服务、两端和 Native Host 需要同步升级。新安装默认持久化元数据，已有配置中的持久化选择保留。

## 验收边界

本地自动测试覆盖并发冷启动复用、崩溃后新实例/凭据、不同来源租约、单端保持在线、无客户端等待、在途任务阻止退出、历史恢复与未知预算保留，以及浏览器并发响应和断线不重放。实际 MV3 与打包 Native Host 已验证自动启动、共用实例、配置读取和浏览器释放后另一端仍在线；普通 Chrome/Edge 界面退出仍需真机验收（当前无头 CDP 关闭接口受持久 Native 连接影响，详见 [兼容性](compatibility.md)）。Windows 注册使用 HKCU，其他操作系统的真实客户端退出、安装器分发与读屏仍需各自环境验收。

安装将 Bridge 和运行依赖复制到助手目录，Native Host 也安装在本机用户目录，服务进程使用安装目录作为工作目录，不依赖项目源码磁盘。仍需要记录的 Node 24 可执行文件。这是本地服务机制，不是已完成签名的一体化安装包。助手目录移动或 Node 路径改变后需重新安装启动入口；扩展白名单改变后，既有服务需退出并由客户端重新启动以载入新授权。
